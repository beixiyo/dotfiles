## 边界

- 评估阶段只读（调研时本次新建的临时源码目录除外）；未获用户明确确认，不修改业务代码、配置或用户已有仓库的 Git 状态，即使结论为可行也要等用户确认
- 克隆得到的第三方代码只读不执行
- 需求模糊时先提 2~3 个具体问题澄清，不编造需求

## 评估依据

- 从相关源码和配置确认现状、目标差距及隐性约束，重点检查上游能力和调用方兼容性
- 已有源码、配置或权威资料足以支持结论时直接使用；依赖未知上游能力、版本差异或未确认 API 行为时，使用 `search` / `github` 查证
- 关键结论附 `path:line` 源码位置或文档链接；只在有助于理解边界时摘录必要片段，不为满足格式复制代码
- 信息不足时说明缺少的证据及其影响，不把推测写成已验证事实

## 按需获取源码

- 优先复用版本匹配的本地源码，但先辨别形态：workspace 链接、本地 fork、包内附源码的可直接读；node_modules 的构建产物（dist、bundle、压缩或类型丢失）适合查事实（.d.ts、导出、字段名、内嵌字符串），查实现逻辑应改查上游对应 tag/commit 的源码，不要硬读混淆产物
- 需要跨目录阅读、搜索大量源码时，对目标分支、tag 或 commit 做浅克隆获取快照，超大仓库再考虑稀疏检出。操作前读取 [源码检出指南](references/source-checkout.md)

## 交付

先给出可行、部分可行或不可行的判断及依据，再按任务需要展开：

- 现状与阻碍目标的具体约束
- 有实际选择时比较候选方案，说明推荐方案与项目约束的关系
- 涉及模块或文件、改动范围、API 兼容性及迁移成本；能可靠估算时给文件数或改动量
- 关键风险、验证方式及未解决问题；不可行时说明替代方向

简单结论用短段落即可，复杂方案可用表格；不强制固定章节、步骤数量或收尾问句
