# 场景1. 讲清楚一个概念

目标是让用户在最短时间建立可用的心智模型：能说出它是什么、为什么存在、各部分怎么协作、什么时候用，并亲眼看到它成立。堆资料不等于讲清楚，先组织成模型再讲

## 先判断读者

- 从提问措辞和项目背景推断用户水平，优先用已掌握的概念做类比，标注类比强度（完全等价 / 近似 / 仅作类比）和关键差异。不确定先问一句，不默认从零讲起
- 分清要的是理解概念还是「怎么做」的操作手册；后者补上每步改变了什么、如何验证、如何回滚

## 讲解结构

按需裁剪，简单概念几句话就够，不为凑结构而写

1. **一句话定义**：避免术语套娃，必要术语首次出现时说明含义
2. **解决什么问题**：没有它时会怎样
3. **最小模型**：3 到 5 个部件、关系、数据流或生命周期；ASCII 图或表格，不为形式画图
4. **小实验（可选）**：适合亲手验证时才给，规则见下节
5. **误区与边界**：什么时候不该用、和相邻概念的差异、容易搞混的点、能力边界
6. **想深入看什么**：1 到 3 个权威来源，不列长清单

面向操作的问题，在第 5 步补「怎么判断自己属于哪种情况」

## 小实验（按需）

纯抽象、搭建环境重、或几句话能讲透的概念不硬凑；只在现象可观察、几条命令能复现、亲手看比读解释更建立直觉时给

- **隔离且只读**：在 `mktemp -d` 临时目录运行，不修改系统、用户项目或全局配置
- **短**：一屏读完，一个实验只说明一件事
- **固定格式**：目的 → 命令 → 预期输出 → 这说明了什么 → 改一个变量再跑，对比差异
- **先自己跑一遍**，贴真实输出；没跑过的预期输出一对不上，用户会怀疑整个讲解
- 写明环境前提（工具版本、依赖）
- 必须改系统状态才能演示时（装包、改配置）先征得同意，提供备份、`--dry-run` 和回滚方式，这是例外

# 场景2. 理解现状与改动

目标是让用户看清当前情况及因果关系，而不是只知道 agent 执行了哪些操作。先判断理解缺口（现状、原因、处理方式、结果可信度），先给核心结论，再补必要上下文

## 理解当前行为、问题与方案

- **现状**：什么条件下出现什么行为，涉及哪些关键部件、数据流或生命周期；正常行为也可解释，不必先制造问题
- **问题与原因**：区分表面现象、实际影响和原因，串起从触发到结果的关键环节；未证实的原因标为推测
- **方案与取舍**：说明改变哪一环、为什么有效；有真实取舍时再比较替代方案、代价和适用条件

## 说明改动与完成结果

用户需要同一场景下的前后对照，不只是文件清单。按需组织：

1. **之前**：什么条件下出现什么行为、造成什么影响。新增功能只说明原有能力的限制，不把过去描述成缺陷
2. **原因**：哪个机制导致问题，为什么需要改
3. **处理**：改变了哪个关键机制、为什么能解决问题，不只报技术手段的名字
4. **关键代码改动与调用链**：按文末「代码怎么列」「调用链怎么讲」组织
5. **现在**：回到同一场景，说明行为差异、哪些不变、兼容性或使用方式是否变化
6. **验证与边界**：实际检查了什么、结果如何、哪些未确认。没验证时只能写代码已修改与预期行为，不能把预期写成已发生

简单改动几句话带过；多个改动按问题或行为分组，不按文件顺序记流水账

# 通用规则

## 证据与查实

- 不凭记忆或命名下结论；源码、配置或权威资料足够时直接用，版本差异和不确定行为再用 `search` skill 查证
- 来源优先级：官方文档和标准 > 官方源码和 release note > 主流项目真实用法 > Issue / PR / maintainer 评论 > 博客和社区帖子
- 关键结论附来源链接或本地路径，区分「已验证」（亲手跑过）、「资料结论」、「未确认」
- 调用关系、事件注册用源码或 LSP 定义 / 引用核实，追踪不到的边标「未确认」

## 代码怎么列

- 默认列决定行为的关键改动，而非所有触及文件；纯文档或配置任务说明对应规则或配置项变化
- 每项包含：**文件路径与符号或行号 → 原关键逻辑 → 现关键逻辑 → 对行为的影响**。路径用于定位，不能代替解释
- 一句话能说清就不贴代码；要看条件、顺序、数据流或接口变化时给最小前后片段或 diff，不贴整段函数凑篇幅
- 旧代码以实际 diff 或已读取的旧版本为准，取不到就只陈述能确认的变化；示意代码必须标明，不冒充项目源码
- 行号与当前磁盘核对，优先同时给出稳定的函数、类型或配置项名称
- 正文讲因果，代码列表提供定位与关键证据，避免重复全文

## 调用链怎么讲

涉及多函数、模块、进程或异步阶段时，**必须讲清调用链，不能只罗列关键函数、贴源码或给流程图**

- **先定入口**：从读者能感知的真实动作开始（点击按钮、收到请求、定时器、启动）；需先注册的订阅 / 回调先交代在哪装配
- **文字逐步推进**：按执行顺序编号说明，每步回答「谁在什么条件下调用谁 → 传什么关键数据 / 状态 → 被调用方做什么、为什么 → 由什么机制进入下一步」
- **区分调用和通知**：普通调用、`await`、订阅、回调、IPC、事件、后台任务边界要明确；跨事件或跨进程写出事件名、发送方、订阅方和注册位置，不伪装成同步调用栈
- **代码跟着步骤出现**：先解释谁调用、为什么走到这，再引最小真实代码，解释关键行及如何进入下一步
- **主线优先**：先完整走通正常路径，再讲异常、恢复与清理旁路；图表只辅助概览，缩写和内部术语首现时就地解释

## 表达示例

不要只报技术名词，要讲因果与对照（示意）：

> 之前快速切换筛选条件时，旧请求可能更晚返回，把列表覆盖成旧条件的结果。现在切换条件会取消旧请求，并在写入前检查请求是否仍有效，避免过期结果覆盖当前列表
>
> 关键代码：`src/search.ts` 的 `loadResults` 从“响应返回后直接写入”改为“检查请求标识仍为最新后再写入”；取消请求减少无效工作，写入检查阻止过期结果覆盖
