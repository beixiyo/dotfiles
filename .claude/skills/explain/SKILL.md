# 讲清楚一个概念

目标是让用户在最短时间建立可用的心智模型：能说出它是什么、为什么存在、各部分如何协作、什么时候用，并亲眼看到它成立。堆资料给用户不等于讲清楚，先组织成模型再讲

## 先判断读者

- 从提问措辞和项目背景推断用户水平，优先用用户已经掌握的概念做类比，并标注类比强度（完全等价 / 近似 / 仅作类比）和关键差异，避免用户把类比当等价。同一个概念对新手和老手的讲法完全不同，不确定时先问一句，不要默认从零讲起
- 分清用户要的是理解概念，还是一份「怎么做」的操作手册。后者要补上每一步改变了什么、如何验证、如何回滚

## 讲解结构

按需裁剪，简单概念几句话就够，不要为了凑结构而写

1. **一句话定义**：第一遍避免术语互相套娃，必要术语第一次出现时说明含义
2. **解决什么问题**：没有它时会怎样，这是理解动机的关键
3. **最小模型**：3 到 5 个部件、它们的关系、数据流或生命周期；用 ASCII 图或表格，不为形式画图
4. **小实验（可选）**：现象适合亲手验证时才给，规则见下节
5. **误区与边界**：什么时候不该用、和相邻概念的差异、容易搞混的点
6. **想深入看什么**：1 到 3 个权威来源，不列一长串

面向操作的问题，在第 5 步补一个「怎么判断自己属于哪种情况」

## 证据

- 不凭记忆下结论。已有源码、配置或权威资料足以回答时直接使用，版本差异和不确定的行为再用 `search` skill 查证
- 来源优先级：官方文档和标准 > 官方源码和 release note > 主流项目的真实用法 > Issue / PR / maintainer 评论 > 博客和社区帖子
- 关键结论附来源链接或本地文件路径；明确区分「已验证」（亲手跑过）、「资料结论」和「未确认」

## 小实验（按需）

不是每个概念都适合。纯抽象的概念、需要大量环境搭建的、或几句话就能讲透的，不要硬凑。只有现象可观察、几条命令能复现，且亲手看到比读解释更能建立直觉时才给

- **隔离且只读**：在 `mktemp -d` 的临时目录里运行，不修改系统、用户项目或全局配置，这样用户可以放心跑，也不需要回滚
- **短**：用户一屏能读完，一个实验只说明一件事
- **固定格式**：目的 → 命令 → 预期输出 → 这说明了什么 → 改一个变量再跑一次，对比差异
- **先自己跑一遍**，贴真实输出。写了没跑过的预期输出，用户一旦对不上就会怀疑整个讲解
- 写明环境前提（工具版本、依赖）
- 必须修改系统状态才能演示时（装包、改配置），先征得用户同意，并提供备份、`--dry-run` 和回滚方式，这是例外

## 输出

- 默认直接在回复里讲。只有用户要求沉淀，或内容会被后续任务复用时，才写 Markdown 文件
- 结尾说明哪些已验证、哪些来自资料、哪些未确认，以及用户下一步可以做什么
